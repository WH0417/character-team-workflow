# 角色协作：设计先行，分层执行

## 角色与拆分

- **设计者默认一个**，作为独立子代理先分析用户问题、补全必要内容与提示词，交付完整设计文档；不直接派发实施任务。
- **总分配者仅一个**，由当前主代理在读取设计交接后承担，负责总目标、顶层分工与最终汇总。
- **工作者可多个**。任务已明确可执行则直接工作；仍跨多个独立模块时，可临时作为子分配者继续调用下级工作者，直到叶子任务足够清晰。子分配者只细分已获授权的范围，不变更总目标，也不把所有工作反复向下转派。
- **每项交付明确配备独立审查责任**。可由一个合适的审查者覆盖多个模块；作者不能审查自己的成果，审查者不能替作者修改后自批通过。

每次派发说明“做什么、负责哪部分、交付什么、由谁审查”。使用真实子代理，提供自包含简报；模型与思考强度继承默认。明确文件归属，依赖和交叉修改按顺序处理。

主代理加载本入口，各子角色按自己的角色简报执行，不自行重启整套流程。工作者可以继续子分配，但不创建第二个总分配者或重复的前置总设计流程。

## 前置设计与提示词交接

1. 主代理先作为流程入口启动独立设计者，交给它用户原始问题、已有资料与约束。设计交接完成前不开始业务分工或实施；入口调用设计者不等于已开始分配实施工作。
2. 设计者输出完整设计文档：原始诉求与目标、必需需求、范围与假设/待澄清项、方案和内容补全、模块与交付物/依赖、可并行任务组与文件归属建议、验收标准、三类计划简图，以及给总分配者的增强提示词。内容完整但按任务规模控制篇幅；具体人数由总分配者结合容量决定。
3. 增强提示词整理成可直接用于分工的任务简报，保留用户本意与约束。明确区分用户要求、合理假设、可选扩展；不能把建议自动升格为必须做的工作，也不编造事实、数据或工具能力。
4. 优先使用用户指定设计文件；否则在任务输出目录保存一份 `设计文档.md`，避免覆盖其他任务的同名文件。增强提示词放在文档末尾即可。写入后通过原生消息或返回结果推送真实路径、关键假设和提示词摘要。
5. 主代理必须实际读取文档，核对目标、边界和验收标准后才进入唯一总分配者职责。默认继续执行；用户明确要求先审方案，或缺少决定性信息时才等待用户，其余合理假设标注后继续。
6. 设计者交接后可结束执行回合，后续设计问题再调用；是否释放名额以宿主状态为准。流程入口与总分配者是同一主代理的前后阶段，不是两个总分配者。

## 并行、自主子分配与人数

- 先划分可交付、可验收的任务组，再定人数。就绪、互不依赖、无写冲突且值得拆分的工作优先并行；前后依赖、共同修改同一文件或很小的工作顺序执行或由同一人负责。共享文件指定整合负责人。
- 先直接复用合适且仍持有名额的空闲角色。需要重新占位的唤醒与新建角色一起进入下式，获得名额后再派发任务。工作者上限指同时占位数，包含子分配者，用户未设置时省略该项。任务数、累计角色数和同时占位数分开记录。

```text
新增／重新占位的工作者数 = max(0, min(
  复用后仍就绪且未分派的任务组数,
  本分配者已获额度内的可用名额,
  宿主实际可新增的名额,
  工作者上限余量（若用户设置）
))
```

- 根层可用额度来自全局未分配名额；子层来自本模块未占用、未另行预留的部分。给下级或审查者预留的名额不可再次分派。
- 总分配者维护一个全局额度，按宿主规则计入所有角色，包括主代理、设计者、子分配者和审查者。模块额度包含自身及全部后代和审查者；子模块从父额度划出，不新增全局额度。预留转占用只改状态，不重复扣减。
- 子分配者可在已获范围和额度内自主创建下级代理，不逐次请求用户确认；创建前登记额度归属，调用后报告实例ID和状态。超额须向上申请调整，未获额度先排队。额度转移须原持有者确认不再使用后登记，避免两方同时使用。
- 创建失败归还预留；结束、等待、空闲或超时不自动释放名额。按宿主状态核对后更新；创建结果不明先查已有角色与任务，再决定重试。
- 仅在模块仍有多个值得拆分的任务时增加层级。无名额则复用、减少层级或分阶段执行；不能让管理者和等待者占满名额。占满前确认独立审查的调度路径；宿主不释放已完成会话或释放机制不明时，提前安排审查额度。无需始终空留一个席位，作者不能充当自己的审查者。
- 自主会话指真实内部子代理，不自动创建用户侧边栏的新聊天。实际并发由宿主决定，不承诺操作系统多线程；模型与思考强度继承默认配置。

## 必须生成三类可视流程图

设计阶段先展示本次计划，分工后记录真实调用与交接，交付时更新为实际过程：

1. **工作图**：用户需求 → 设计者 → 完整设计文档/增强提示词 → 总分配者划分任务 → 额度内并行或排队顺序执行 → 审查 → 交付或返工。
2. **调用图**：入口启动设计者、文档交回同一主代理后进入唯一总分配者阶段、真实子分配层级与审查者；标明额度归属、实际并行分支、向上反馈与必要的设计回退。
3. **讨论图**：问题 → 设计者/分配者/工作者回应或反驳 → 核对证据 → 设计修订、实施返工、撤回误判或保留分歧 → 复查。

使用可渲染 Mermaid，并提供可直接查看的 SVG／PNG 兼容输出；只有文字列表或图源码不算完成。无争议／驳回时在实际图上标“未触发”，不伪造事件。图保持简明，详细记录放一份流程记录即可。

可用本 skill 的辅助脚本把节点和边渲染为 SVG／PNG：

```text
node scripts/render-flowcharts.cjs input.json output.svg output.png
```

在 skill 目录解析脚本路径，在任务目录保存输出。输入是 `{title, charts:[{title,nodes:[{id,label,row,col}],edges:[{from,to,label?,dashed?}]}], note?}`；三个 chart 分别表示上述流程，row/col 从 0 开始。PNG 需要宿主已有的 Playwright 和浏览器；依赖不可用时提供可查看的 SVG，不临时安装依赖。

## 执行与分层调用

1. 总分配者依据已读取的设计文档和增强提示词，按就绪任务和全局额度分派。子分配者在范围及额度内自主细化模块、调用工作者并安排独立审查；任务应逐层更具体。
2. 叶子工作者实际产出，返回文件、检查证据和未解决问题。子分配者汇合成果、接口和审查结果，逐级向上反馈。
3. 各级审查者依据原要求和真实成果独立检查，给出“通过／驳回／无法验证”，说明证据；不预设通过结论。
4. 角色可直接向已有队友请求协助、提问或反驳。新增下级实例由负责该模块的分配者调用，避免重复派发同一任务。
5. 用本次任务的 `流程记录.md` 维护一份任务表：任务ID、负责人/实例ID、依赖、状态、交付物/检查证据、名额归属与占用；旁记全局容量和模块额度。各级在派发前登记自身任务与占额，子分配者通过消息报告变化；共享文件仅由总分配者写入。中断恢复先核对实际状态，只继续未完成及受影响项，不重建整队。
6. 最终交付设计文档、实际成果、审查结论和三类实际流程图，说明真实参与角色、重要异议及尚未完成项。

工作者提供自检证据，审查者独立核对关键风险。各级分配者复用同一版本的有效证据，避免逐层重复全量检查；成果、输入或要求改变，证据不足或出现新问题时再验证相关部分。作者自检和证据复用均不代替独立审查。

## 审查驳回与讨论

审查者有权直接质疑设计者、工作者、子分配者或总分配者。认为成果质量不足时，指出不满足的要求、证据和返工要求，可驳回局部成果或整项交付，要求修改或重新做。

设计者、工作者和分配者都可以反驳误判。能用检查或实验核对的先验证；问题成立则交对应责任角色修改或重做，再由独立审查者复查。分配者不能把仍然成立的驳回直接改成通过；审查者可以依据新证据撤回误判或通过修订版，均要记录。

设计问题成立或用户改变需求时，退回设计者修订文档，再由总分配者同步受影响任务并安排复查；普通实施缺陷仍退回工作者。用户原要求优先，不能通过降低验收标准掩盖实施失败。不新增默认的设计审批或额外审查关卡。

同一争议默认最多两轮回应；同一问题两轮修改仍未通过时停止无效循环，向上报告未通过及后续选项。轮数结束不等于验收通过。不为展示人格制造争议，也不通过提高无关标准扩大用户任务。

## 宿主工具与范围

使用当前宿主提供的创建代理、消息、追问和等待工具，例如 `spawn_agent`、`send_message`、`followup_task`、`wait_agent`；参数以工具说明为准。空闲角色需要追问唤醒，消息投递成功不等于已经执行。

角色沿用任务授权和工作目录。宿主缺少独立代理或消息能力时说明限制，不把单代理模拟发言标记为独立执行。
